# HNWS Photos

ログイン不要で閲覧できる画像一覧と、MCIDで検索できるアルバム。管理者だけがブラウザーから画像を追加・削除できます。白と淡い緑を基調としたレスポンシブUI、画像の拡大・前後移動、60件ずつの表示、遅延読み込みに対応しています。

閲覧UIはHTML/CSS/JavaScriptです。管理者認証とアップロード処理にはPython/Flaskを使用します。**静的ホスティングだけでは管理機能は動きません。** VPSや自宅サーバーなどの永続ディスクに保存し、Cloudflareを手前に置く構成です。R2、外部DB、Immichへの接続は不要です。

## Docker Composeで起動

Docker EngineとDocker Compose v2が入ったサーバーで実行します。Pythonの手動インストール、設定ファイル作成、事前の管理者登録は不要です。

```sh
git clone https://github.com/yukugura/img-site.git
cd img-site
docker compose up -d
```

ブラウザーで **`http://サーバーのIP:8088`** を開くと初回セットアップが表示されます。初回は公開済みコンテナイメージを取得します。GitHub Actionsによる初回配布が完了し、GHCRパッケージが公開されている必要があります。

1. `docker compose logs web` で初回設定コードを確認します。
2. 画面にコード、新しい管理者パスワード（12文字以上）、確認用パスワードを入力します。
3. 「設定してはじめる」を押すと管理者としてログインし、画像をアップロードできます。

初回設定コードは第三者による管理者登録を防ぐためのものです。秘密のコードなのでログを公開しないでください。コードはセットアップ後に無効になり、設定済みのサーバーでは初回登録APIも閉じます。以後、一般ユーザーはログイン不要です。管理者は `/admin` からログインします。再起動・コンテナ再作成後も設定と写真は保持されます。

```sh
# 状態確認
docker compose ps
# 更新（通常の更新時）
docker compose pull
docker compose up -d
# 停止（データは保持）
docker compose down
```

`docker compose down -v` は保存ボリュームも削除します。通常の停止・更新では使わないでください。

### イメージを取得して更新する

```sh
sudo docker compose pull
sudo docker compose up -d
```

`pull` は新しいイメージのダウンロードだけで、実行中のコンテナは更新しません。`up -d` がコンテナを入れ替えます。両方を実行する `sudo ./update.sh` も利用できます。画像・DB・管理者設定は同じボリュームに保持されます。`down -v` は使いません。Composeファイルや設定項目に変更があるリリースでは、先に `git pull origin main` も実行してください。

旧版からの初回移行は `git pull origin main` の後、上記2コマンドを実行します。`.env`・同じディレクトリ名・Composeプロジェクト名を維持してください。配布元は `ghcr.io/yukugura/img-site:latest`。`.env` の `IMAGE_TAG` に `sha-<完全なコミットSHA>` を指定してバージョンを固定することもできます。DB形式を変更した版からの旧版への巻き戻しは保証しないため、更新前にバックアップしてください。

**配布側の初回設定**: `.github/workflows/publish.yml` がmainへのpush後にテストし、amd64/arm64イメージをGHCRへ配布します。GitHubのActionsを有効にし、最初の成功後にPackagesの `img-site` → Package settings → Change visibilityでPublicにしてください。初期のパッケージがPrivateだと一般の `docker compose pull` は拒否されます。ワークフローはGitHubが発行する `GITHUB_TOKEN` を使い、ユーザーのトークンをリポジトリへ保存しません。

配布前や開発用にソースからビルドする場合は、次を使います。

```sh
docker compose -f compose.yaml -f compose.build.yaml up -d --build
```

### パスワードを忘れた・ログインできない場合

管理者のユーザー名は `admin` 固定です。ブラウザーの標準フォーム送信と `autocomplete` を使用し、パスワードの保存・自動入力に対応しています。保存ダイアログの表示はブラウザー側の設定によります。入力欄の表示切替とCaps Lock表示も利用できます。

サーバーのターミナルで、入力したパスワードが現在保存されているものと一致するか調べられます。入力は非表示で、コマンド履歴やログにパスワードを残しません。

```sh
sudo docker compose exec web python manage.py check-password
```

一致するのにブラウザーでログインできない場合は、[診断手順](docs/DEPLOYMENT.md#ログイン失敗の切り分け)でHTTPステータス・Cookie・PUBLIC_URL・NPMの設定を確認します。一致しないだけでは、いつ入力を間違えたのか、以前設定した別のパスワードなのかまでは判定できません。

忘れた場合は再設定します。

```sh
sudo docker compose exec web python manage.py reset-password
```

新しいパスワードを2回入力します。画像・アルバム・アイコンは保持され、試行回数制限を解除し、古いログインを失効させます。この版では全ワーカーが次のリクエストから新しいパスワードを読み取るため、再起動は不要です。Webコンテナが起動できない場合は `sudo docker compose run --rm --no-deps --entrypoint python web manage.py reset-password` を使えます。`ADMIN_PASSWORD_HASH` を独自に環境変数で設定している構成では、その設定側を変更してコンテナを再作成してください。

設定状態だけを表示するコマンドもあります（パスワードや鍵は表示しません）。

```sh
sudo docker compose exec web python manage.py status
```

### ポート・HTTPS

標準は全インターフェースの8088番でHTTP配信します。初回設定は信頼できるLAN内、またはHTTPS経由で実施してください。公開HTTPSの証明書とドメインは、既存のリバースプロキシで設定します。

必要な場合だけ `.env.example` を `.env` にコピーして変更します。別ポートなら `PORT=8090`。同じサーバーのHTTPSリバースプロキシからのみ接続させる場合は次のように設定します。

```dotenv
BIND_ADDRESS=127.0.0.1
PORT=8088
COOKIE_SECURE=1
TRUST_PROXY=1
```

変更後は `docker compose up -d` で反映します。プロキシの転送先は `http://127.0.0.1:8088`。`X-Forwarded-Proto` をプロキシ側で上書きしてください。HTTPSを設定する前に `COOKIE_SECURE=1` にするとHTTPでログインを維持できなくなります。`TRUST_PROXY=1` は信頼できるプロキシ経由の場合だけ使います。

### 保存とバックアップ

標準設定では画像・DB・管理者設定はDockerの名前付きボリューム `gallery-data`（実名にはComposeプロジェクト名が付きます）に保存します。GitやDockerイメージにユーザーの画像、MCID、パスワードを含めません。管理者設定はハッシュで保存し、セッション鍵も自動生成します。写真を投稿すれば、公開サイトのアルバム名・ファイル名としてMCIDが表示されるのは従来どおりです。

同じプロジェクト名・ディレクトリ名で再起動してください。名前を変えると別のボリュームが作成され、初期状態に見える場合があります。Docker化前の `data/` は自動では取り込まれません。

バックアップ例（DBと写真の整合性を保つため一時停止します）：

```sh
mkdir -p backups/config backups/images
docker compose stop web
docker compose cp web:/data/. ./backups/config/
docker compose cp web:/storage/media/. ./backups/images/
docker compose start web
```

バックアップには管理者設定と秘密鍵が含まれます。公開したりGitに追加したりしないでください。リポジトリ内の `backups/` はGitとDockerビルドから除外しています。復旧時は新しいボリュームにデータを戻し、コンテナ内UID/GID 10001が読み書きできる所有権にしてください。

### Pythonでの開発（任意）

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.lock
.venv/bin/python bootstrap.py # DATA_DIRを指定しない場合の保存先はdata/
COOKIE_SECURE=0 .venv/bin/gunicorn --bind 127.0.0.1:8000 'app:create_app()'
```

CLIの `manage.py` で管理者を事前登録する方法も残しています。管理者は共通アカウント1つ、セッションは8時間です。ログインは全体で5分間に10回までです。

## NPM + Cloudflareで公開する

[公開手順](docs/DEPLOYMENT.md)にNPMの転送設定、CloudflareのDNS・SSL、一般ユーザーへ共有するURLをまとめています。閲覧URLは公開ドメインのトップページで、発行・登録操作は不要です。標準のホスト側ポートは **8088**、`.env` の `PORT` で変更できます。

## 管理画面と表示機能

左下の管理者ログインから、次の操作ができます。

- **表示名の変更**: アルバムの名前を日本語など任意の1〜80文字に変更。内部のMCID・自動分類・URLは変えません。
- **画像の複数選択**: 写真のチェックボックス、または検索結果の「一覧を選択」（最大500枚）でまとめて削除・非表示・公開できます。
- **アルバムの削除**: 表示中・非表示の全画像と旧IDの対応関係を削除します。取り消しはできません。削除後に同じMCIDの画像を追加すると、新しいアルバムが作られます。
- **非表示**: 一般ユーザーの一覧から除外し、オリジンサーバーでの公開画像URLへのアクセスも拒否します。管理者には非表示バッジ付きで表示します。Cloudflareやブラウザーに残る既存キャッシュには別途対応が必要です。[更新時のキャッシュ対応](docs/DEPLOYMENT.md#非表示機能とキャッシュ旧版からの更新時に必須)を必ず確認してください。
- **アイコン変更**: 管理画面から2MB未満・100万画素以内のPNG/JPEG/WebP/ICOをアップロード。ブラウザータブに反映します。左上にはロゴ1つだけを表示します。アップロードされたアイコンはGitに含めず永続保存します。アイコン未設定時はタブのみ添付ロゴを代用します。

添付のロゴをサイト左上に配置し、クリックするとページ先頭へスクロールします。アルバムのサムネイルは正方形です。画像モーダルはPCのホイール・ドラッグ、スマートフォンのピンチ・ドラッグで1〜8倍に拡大縮小でき、倍率ボタンからも操作できます。写真・アルバム一覧は末尾に近づくと60件ずつ自動追加します。手動読み込みボタンもアクセシビリティ用の代替として残しています。

画像の保存先は `.env` の `MEDIA_STORAGE` で変更できます。[保存先の変更・移行手順](docs/DEPLOYMENT.md#画像の保存先を変更する)を参照してください。

## アルバムの統合

管理者ログイン後、「アルバムを統合する」を開き、旧IDのアルバムと統合先のMCIDを指定します。統合先は既存のアルバムでも新しいIDでも構いません。確認後、画像を削除せずに移動します。

- 今後、旧IDのファイル名でアップロードした画像も統合先に入ります。
- 旧IDでの検索と以前のアルバムURLも引き続き使えます。
- さらに別のIDへ統合した場合も、古いIDすべてが最終的な統合先を参照します。
- 未分類は統合対象にしません。同じアルバムへの統合や循環は拒否します。
- 画面からの取り消しはありません。実行前にIDを確認し、必要ならバックアップしてください。旧IDと統合先の対応も公開一覧に含まれます。

[セキュリティ対策と検証範囲](docs/SECURITY.md)も参照してください。

## アルバム分け

`<MCID>_<数字>.<拡張子>` に一致するとMCIDのアルバムに入ります。一覧に存在しない新しいMCIDも自動分類します。MCIDには英数字・アンダースコア・ハイフンを使用できます。

| ファイル名 | アルバム |
|---|---|
| `demo_user_10001.png` | `demo_user` |
| `sample-user_10002.png` | `sample-user` |
| `my_mcid_123.jpg` | `my_mcid` |
| `example_user_10003_negative_film.png` | `example_user` |
| `example_user_10004_aged.png` | `example_user` |
| `example_user_10004_negative.png` | `example_user` |
| `旅行.png` / `player_123_other.png` | 未分類 |

対応画像はPNG/JPEG/WebP、1枚20MB・1200万画素以内です。命名規則に一致しなくても画像として有効なら受け付けます。同名・同内容は重複登録しません。同名で内容が違う画像は別画像になります。MCID検索は大文字小文字を区別しませんが、アルバムの分類はファイル名の表記を保ちます。

アップロード時に向きを補正し、メタデータを引き継がないPNGと、長辺320px以内のWebPサムネイルを生成します。元サイズは保ちますが元ファイルのバイト列は保持しません。アニメーションは先頭フレームのみです。サムネイルは切り抜かず保存し、一覧上では正方形にトリミング表示します。

## 既存画像の取り込み

Immichなどから画像をダウンロードし、元のファイル名を保ったまま管理画面で複数選択してください。1枚ずつ順に送るので、大量選択でもリクエスト全体が巨大になりません。失敗した画像名を表示し、同じ選択の再送も可能です。ブラウザーは処理が終わるまで開いておきます。

実際のファイル名一覧や写真はリポジトリに含めません。ドキュメントとテストのIDは架空の例です。Immichからの自動移行は実装していません。

## Cloudflare Cache Rules

DNSのプロキシを有効にし、SSL/TLSは **Full (strict)** を使用してください。オリジン側にも有効な証明書が必要です。

| 対象 | 設定 |
|---|---|
| `/media/*` | キャッシュ対象。Origin Cache-Controlを尊重。画像はSHA-256名、非表示の反映のためエッジ最大60秒・ブラウザー再検証、`public, max-age=0, s-maxage=60, must-revalidate` |
| `/catalog.json` | Cache Everything相当の「キャッシュ対象」に設定し、Origin Cache-Controlを尊重。エッジ60秒・ブラウザーは再検証 |
| `/api/*`・`/auth/*` と `/admin`・`/setup` | **キャッシュをバイパス**。APIは `private, no-store` |
| `/` と `/static/*`・`/site-icon.png`・`/favicon.ico` | Origin Cache-Controlの `no-cache` を尊重。HTML/JS更新時の取り違えを防止 |

サイト全体への一律「Cache Everything」は設定しないでください。既存ルールがある場合はAPIバイパスが優先されるよう確認します。追加した画像が公開一覧に反映されるまで最大60秒かかります。即時反映には `/catalog.json` をパージします。

**画像を完全に取り下げる場合:** 管理画面での削除はオリジンの画像とDBを削除します。Cloudflareに残った `/media/<hash>.png`、`/media/<hash>-320.webp` と `/catalog.json` をURL指定でパージしてください。削除前の拡大画面「元のサイズで開く」からハッシュを確認できます。削除APIもパージ対象のパスを返します。すでに閲覧者がダウンロード・ブラウザーキャッシュしたコピーは回収できません。自動パージは未実装です。

## 検証

```sh
.venv/bin/python -m pytest -q
node --check static/app.js
```

初回設定・二重登録の防止・再起動後の認証、分類、未分類アップロード、画像検証、重複判定、サムネイル、公開閲覧、認証・CSRF、ログアウト、ログイン制限、削除とキャッシュヘッダーを検証します。

### CPU・メモリと同時アクセス

Webコンテナの標準上限はCPU 1コア相当・メモリ768MBです。LXCに割り当てるCPU/RAMを増やしても、この上限は自動では増えません。`.env` の `WEB_CPUS` と `WEB_MEMORY_LIMIT` を変更し、`docker compose up -d` で再作成します。例としてLXCに4コア・4GBを割り当て、他サービスの負荷が小さい場合は `WEB_CPUS=2.0`、`WEB_MEMORY_LIMIT=2g` を試せます。LXC全体の上限以上は使えません。OS・NPMなどのための余裕も残してください。

Gunicornは現在2ワーカー×2スレッドです。CPU/RAMを増やしてもワーカー数は変わりません。「100人が閲覧中」と「100件の画像リクエストが同時にオリジンへ来る」は異なります。Cloudflareの公開画像キャッシュ、回線速度、画像数、初回アクセス時の負荷に左右されるため、100人への対応を保証するには実データ相当の負荷試験が必要です。`docker stats` と応答時間・エラー率を確認して調整してください。認証APIはキャッシュしないでください。

アップロードは現在1枚ずつです。並列化する場合は、まず2件程度の上限付き処理が候補です。画像展開・サムネイル生成のメモリとCPU負荷、SQLiteの書き込み待ち、閲覧への影響を確認してから増やします。2000件を一斉送信する方式にはしません。

管理者画面の「非表示のみ表示」で、非表示にした画像だけに絞り込めます。アルバム一覧・アルバム内・検索と併用でき、「すべての画像に戻す」で解除できます。切り替え時は選択を解除します。一般ユーザーには表示されません。
